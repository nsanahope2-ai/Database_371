## Problem Summary

A library charges a hypothetical fine of **K2.00** for each day after `due_on`. Returning a book on or before `due_on` attracts **K0.00** fine, and once returned, a loan stops accumulating further fines. All database objects are isolated inside schema `q03_library`.

---

## (a) Database Schema and Seed Data [6 Marks]

### Design & Constraints
- **`books`**: `book_id` (PK), `title` (non-empty `VARCHAR(200)`).
- **`loans`**: `loan_id` (PK), `book_id` (FK referencing `books`), `borrower_name`, `borrowed_on`, `due_on`, `returned_on` (`NULL` while unreturned), and `fine_amount` (`DEFAULT 0.00`), enforcing:
  - `due_on >= borrowed_on` (`chk_loans_due_after_borrowed`)
  - `returned_on IS NULL OR returned_on >= borrowed_on` (`chk_loans_returned_after_borrowed`)
  - `fine_amount >= 0` (`chk_loans_nonnegative_fine`)
- **`loan_audit`**: `audit_id` (PK), `loan_id` (FK referencing `loans`), `old_returned_on`, `new_returned_on`, `changed_at`.
- **`overdue_summary`**: `snapshot_date` (PK), `overdue_count`, `total_fine`.
- **Seed Data**: 3 books and 6 loans defined using `CURRENT_DATE` offsets so open-overdue, open-on-time, returned-on-time (`0.00`), and returned-late (`10.00`) states remain deterministic regardless of the execution date.

```sql
DROP SCHEMA IF EXISTS q03_library CASCADE;
CREATE SCHEMA q03_library;
SET search_path TO q03_library, public;

CREATE TABLE books (
    book_id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title   VARCHAR(200) NOT NULL CHECK (LENGTH(TRIM(title)) > 0)
);

CREATE TABLE loans (
    loan_id       INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    book_id       INT NOT NULL REFERENCES books(book_id) ON DELETE RESTRICT,
    borrower_name VARCHAR(150) NOT NULL CHECK (LENGTH(TRIM(borrower_name)) > 0),
    borrowed_on   DATE NOT NULL,
    due_on        DATE NOT NULL,
    returned_on   DATE NULL,
    fine_amount   NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    CONSTRAINT chk_loans_due_after_borrowed
        CHECK (due_on >= borrowed_on),
    CONSTRAINT chk_loans_returned_after_borrowed
        CHECK (returned_on IS NULL OR returned_on >= borrowed_on),
    CONSTRAINT chk_loans_nonnegative_fine
        CHECK (fine_amount >= 0)
);

CREATE TABLE loan_audit (
    audit_id        INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    loan_id         INT NOT NULL REFERENCES loans(loan_id) ON DELETE CASCADE,
    old_returned_on DATE NULL,
    new_returned_on DATE NULL,
    changed_at      TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE overdue_summary (
    snapshot_date DATE PRIMARY KEY,
    overdue_count INTEGER NOT NULL CHECK (overdue_count >= 0),
    total_fine    NUMERIC(12, 2) NOT NULL CHECK (total_fine >= 0)
);
```

## (b) Fine Calculation Function: `fn_loan_fine` [6 Marks]

### Logic
- Rejects `NULL` arguments and raises an exception if `p_loan_id` does not exist in `loans`.
- Caps the effective evaluation date at `LEAST(p_as_of, returned_on)` whenever `returned_on IS NOT NULL`, ensuring a returned loan stops accumulating fines after its return date while still supporting historical point-in-time queries (`p_as_of < returned_on`).
- Clamps overdue days with `GREATEST(effective_date - due_on, 0)` so returns on or before `due_on` yield `0.00`.

```sql
CREATE OR REPLACE FUNCTION fn_loan_fine(
    p_loan_id INT,
    p_as_of   DATE
)
RETURNS NUMERIC(10, 2)
LANGUAGE plpgsql
AS $$
DECLARE
    v_due_on         DATE;
    v_returned_on    DATE;
    v_effective_date DATE;
    v_overdue_days   INTEGER;
BEGIN
    IF p_loan_id IS NULL THEN
        RAISE EXCEPTION 'Loan ID (p_loan_id) cannot be NULL.';
    END IF;

    IF p_as_of IS NULL THEN
        RAISE EXCEPTION 'As-of date (p_as_of) cannot be NULL.';
    END IF;

    SELECT due_on, returned_on
      INTO v_due_on, v_returned_on
      FROM loans
     WHERE loan_id = p_loan_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Loan ID % does not exist.', p_loan_id;
    END IF;

    v_effective_date := CASE
        WHEN v_returned_on IS NOT NULL THEN LEAST(p_as_of, v_returned_on)
        ELSE p_as_of
    END;

    v_overdue_days := GREATEST(v_effective_date - v_due_on, 0);

    RETURN (v_overdue_days * 2.00)::NUMERIC(10, 2);
END;
$$;
```

## (c) Return Procedure: `pr_return_loan` [8 Marks]

### Logic
- Acquires a row-level lock (`SELECT ... FOR UPDATE`) on the target loan to prevent concurrent double-return anomalies.
- Rejects `NULL` inputs, non-existent `p_loan_id`, already-returned loans (`returned_on IS NOT NULL`), and invalid return dates (`p_returned_on < borrowed_on`).
- Computes `v_final_fine := fn_loan_fine(p_loan_id, p_returned_on)` and stores both `returned_on` and `fine_amount` in a single atomic `UPDATE`.

```sql
CREATE OR REPLACE PROCEDURE pr_return_loan(
    p_loan_id     INT,
    p_returned_on DATE
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_borrowed_on DATE;
    v_returned_on DATE;
    v_final_fine  NUMERIC(10, 2);
BEGIN
    IF p_loan_id IS NULL THEN
        RAISE EXCEPTION 'Loan ID (p_loan_id) cannot be NULL.';
    END IF;

    IF p_returned_on IS NULL THEN
        RAISE EXCEPTION 'Return date (p_returned_on) cannot be NULL for loan ID %.', p_loan_id;
    END IF;

    SELECT borrowed_on, returned_on
      INTO v_borrowed_on, v_returned_on
      FROM loans
     WHERE loan_id = p_loan_id
       FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Loan ID % does not exist.', p_loan_id;
    END IF;

    IF v_returned_on IS NOT NULL THEN
        RAISE EXCEPTION 'Loan ID % has already been returned on %.', p_loan_id, v_returned_on;
    END IF;

    IF p_returned_on < v_borrowed_on THEN
        RAISE EXCEPTION 'Return date (%) cannot be earlier than borrowed_on (%) for loan ID %.',
            p_returned_on, v_borrowed_on, p_loan_id;
    END IF;

    v_final_fine := fn_loan_fine(p_loan_id, p_returned_on);

    UPDATE loans
       SET returned_on = p_returned_on,
           fine_amount = v_final_fine
     WHERE loan_id = p_loan_id;
END;
$$;
```

## (d) Audit Trigger on `returned_on` Changes [8 Marks]

### Logic
- Uses `WHEN (OLD.returned_on IS DISTINCT FROM NEW.returned_on)` on the `AFTER UPDATE` row trigger.
- Unlike `<>` (which evaluates to `UNKNOWN` when `OLD.returned_on` is `NULL`), `IS DISTINCT FROM` treats `NULL` values as comparable:
  - Fires when `NULL -> DATE`, `DATE -> different DATE`, or `DATE -> NULL`.
  - Suppresses execution when `NULL -> NULL` or `DATE -> same DATE` (e.g., updating `borrower_name`).

```sql
CREATE OR REPLACE FUNCTION fn_trg_audit_loan_return()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO loan_audit (loan_id, old_returned_on, new_returned_on, changed_at)
    VALUES (NEW.loan_id, OLD.returned_on, NEW.returned_on, CURRENT_TIMESTAMP);

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_loans_audit_returned_on
AFTER UPDATE ON loans
FOR EACH ROW
WHEN (OLD.returned_on IS DISTINCT FROM NEW.returned_on)
EXECUTE FUNCTION fn_trg_audit_loan_return();
```

## (f) Partial Index and `EXPLAIN` Plan [5 Marks]

### Index Justification
Over a library's operational lifetime, the vast majority of rows in `loans` represent **returned historical loans** (`returned_on IS NOT NULL`), while only a small fraction are currently checked out (`returned_on IS NULL`). Creating a **partial index** `ON loans (book_id) WHERE returned_on IS NULL`:
1. Excludes all returned historical rows from the B-tree, drastically shrinking index storage footprint and keeping active entries cached in shared buffers.
2. Avoids unnecessary index bloat for historical loans while directly answering availability/circulation lookups (`WHERE book_id = ? AND returned_on IS NULL`).

```sql
CREATE INDEX idx_loans_book_unreturned
    ON loans (book_id)
 WHERE returned_on IS NULL;

ANALYZE loans;

SELECT loan_id, book_id, borrower_name, borrowed_on, due_on
  FROM loans
 WHERE book_id = 1
   AND returned_on IS NULL
 ORDER BY loan_id;
```

## (g) Daily Overdue Summary Job: `pr_refresh_overdue` [6 Marks]

### Logic & Idempotency
- Counts loans that were borrowed on or before `p_as_of`, due before `p_as_of` (`due_on < p_as_of`), and still unreturned as of `p_as_of` (`returned_on IS NULL OR returned_on > p_as_of`), summing their exact point-in-time fines via `fn_loan_fine(loan_id, p_as_of)`.
- Uses `INSERT ... ON CONFLICT (snapshot_date) DO UPDATE` so rerunning the job for the same `snapshot_date` replaces the existing snapshot cleanly without duplicate-key failures or double-counting.

```sql
CREATE OR REPLACE PROCEDURE pr_refresh_overdue(p_as_of DATE)
LANGUAGE plpgsql
AS $$
DECLARE
    v_overdue_count INTEGER;
    v_total_fine    NUMERIC(12, 2);
BEGIN
    IF p_as_of IS NULL THEN
        RAISE EXCEPTION 'Snapshot date (p_as_of) cannot be NULL.';
    END IF;

    SELECT COUNT(*)::INTEGER,
           COALESCE(SUM(fn_loan_fine(l.loan_id, p_as_of)), 0.00)::NUMERIC(12, 2)
      INTO v_overdue_count, v_total_fine
      FROM loans l
     WHERE l.borrowed_on <= p_as_of
       AND l.due_on < p_as_of
       AND (l.returned_on IS NULL OR l.returned_on > p_as_of);

    INSERT INTO overdue_summary (snapshot_date, overdue_count, total_fine)
    VALUES (p_as_of, v_overdue_count, v_total_fine)
    ON CONFLICT (snapshot_date) DO UPDATE
        SET overdue_count = EXCLUDED.overdue_count,
            total_fine    = EXCLUDED.total_fine;
END;
$$;
```

### Daily `00:10` Schedule (`pg_cron`) & Local Windows PostgreSQL 18.6 Note
On Linux/cloud PostgreSQL instances with `pg_cron` enabled, the job is scheduled daily at **00:10** (`10 0 * * *`):

```sql

    'q03_daily_overdue_refresh',
    '10 0 * * *',
    'CALL q03_library.pr_refresh_overdue(CURRENT_DATE);'
);
```
