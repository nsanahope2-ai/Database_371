## Problem Summary

A water utility bills monthly meter readings using a two-band progressive tariff:
- **Zero consumption (`0` units):** `K0.00`
- **First `10` units (`0 < units <= 10`):** `K5.00` per unit
- **Units above `10` (`units > 10`):** `K50.00` for the first `10` units plus `K8.00` per unit above `10`

Each reading stores `previous_reading` and `current_reading`, enforces one reading per customer per month, prevents backward or negative meter values via a row trigger (even during direct SQL imports), generates one bill per reading, tracks overdue unpaid balances through a view and partial index, and snapshots total unpaid receivables daily at `00:30`.

### (a) Database Schema and Seed Data `[6 marks]`

Four normalized tables are created in `q07_water_billing`:

```sql
CREATE TABLE customers (
    customer_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name   VARCHAR(120) NOT NULL CHECK (btrim(full_name) <> '')
);

CREATE TABLE readings (
    reading_id       INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id      INTEGER NOT NULL REFERENCES customers(customer_id) ON DELETE RESTRICT,
    reading_month    DATE NOT NULL
                     CHECK (reading_month = date_trunc('month', reading_month)::date),
    previous_reading NUMERIC(10,2) NOT NULL CHECK (previous_reading >= 0),
    current_reading  NUMERIC(10,2) NOT NULL CHECK (current_reading >= 0),
    CONSTRAINT uq_readings_customer_month UNIQUE (customer_id, reading_month)
);

CREATE TABLE bills (
    bill_id     INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    reading_id  INTEGER NOT NULL UNIQUE REFERENCES readings(reading_id) ON DELETE RESTRICT,
    charge      NUMERIC(10,2) NOT NULL CHECK (charge >= 0),
    amount_paid NUMERIC(10,2) NOT NULL DEFAULT 0.00
                CHECK (amount_paid >= 0 AND amount_paid <= charge),
    due_on      DATE NOT NULL
);

CREATE TABLE receivable_snapshot (
    snapshot_date DATE PRIMARY KEY,
    total_due     NUMERIC(12,2) NOT NULL CHECK (total_due >= 0)
);
```

### (b) Tariff Function `fn_water_charge` `[6 marks]`

```sql
CREATE OR REPLACE FUNCTION fn_water_charge(p_units NUMERIC)
RETURNS NUMERIC(10,2)
LANGUAGE plpgsql
IMMUTABLE
AS $$
DECLARE
    v_charge NUMERIC(10,2);
BEGIN
    IF p_units IS NULL OR p_units < 0 THEN
        RAISE EXCEPTION 'Invalid water consumption (%): units must be non-null and non-negative.', p_units;
    END IF;

    IF p_units = 0 THEN
        v_charge := 0.00;
    ELSIF p_units <= 10 THEN
        v_charge := ROUND(p_units * 5.00, 2)::NUMERIC(10,2);
    ELSE
        v_charge := ROUND((10 * 5.00) + ((p_units - 10) * 8.00), 2)::NUMERIC(10,2);
    END IF;

    RETURN v_charge;
END;
$$;
```

```text
----------------+------------------+-----------------+-----------------+--------------------
           0.00 |            32.50 |           50.00 |           90.00 |             116.00
```
- `fn_water_charge(NULL)` and `fn_water_charge(-2.50)` both raise exceptions (`[PASS]` verified in `DO` block).

### (c) Billing Procedure `pr_generate_bill` `[8 marks]`

```sql
CREATE OR REPLACE PROCEDURE pr_generate_bill(
    p_reading_id INTEGER,
    p_due_on     DATE
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_prev        NUMERIC(10,2);
    v_curr        NUMERIC(10,2);
    v_consumption NUMERIC(10,2);
    v_charge      NUMERIC(10,2);
BEGIN
    IF p_reading_id IS NULL THEN
        RAISE EXCEPTION 'Reading ID must not be NULL.';
    END IF;

    IF p_due_on IS NULL THEN
        RAISE EXCEPTION 'Bill due date (p_due_on) must not be NULL.';
    END IF;

    SELECT previous_reading, current_reading
    INTO v_prev, v_curr
    FROM readings
    WHERE reading_id = p_reading_id
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Reading ID % does not exist.', p_reading_id;
    END IF;

    IF EXISTS (SELECT 1 FROM bills WHERE reading_id = p_reading_id) THEN
        RAISE EXCEPTION 'A bill already exists for reading ID %.', p_reading_id;
    END IF;

    v_consumption := v_curr - v_prev;
    v_charge      := fn_water_charge(v_consumption);

    INSERT INTO bills (reading_id, charge, amount_paid, due_on)
    VALUES (p_reading_id, v_charge, 0.00, p_due_on);
END;
$$;
```

- Locks the parent `readings` row `FOR UPDATE` so concurrent sessions cannot double-bill the same reading, complemented by `UNIQUE (reading_id)` on `bills`.
- Verified rejection of duplicate bill (`reading_id = 3`), unknown reading (`reading_id = 9999`), and `NULL` `p_due_on`.

### (d) Meter Validation Trigger `trg_readings_validate` `[8 marks]`

```sql
CREATE OR REPLACE FUNCTION fn_trg_validate_reading()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.previous_reading IS NULL OR NEW.current_reading IS NULL THEN
        RAISE EXCEPTION 'Meter readings cannot be NULL.';
    END IF;

    IF NEW.previous_reading < 0 OR NEW.current_reading < 0 THEN
        RAISE EXCEPTION 'Meter readings must be non-negative (previous=%, current=%).',
            NEW.previous_reading, NEW.current_reading;
    END IF;

    IF NEW.current_reading < NEW.previous_reading THEN
        RAISE EXCEPTION 'Invalid meter reading for customer % in %: current_reading (%) is less than previous_reading (%).',
            NEW.customer_id, NEW.reading_month, NEW.current_reading, NEW.previous_reading;
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_readings_validate
BEFORE INSERT OR UPDATE ON readings
FOR EACH ROW
EXECUTE FUNCTION fn_trg_validate_reading();
```

- Because `trg_readings_validate` is a `BEFORE INSERT OR UPDATE` row-level trigger on `readings`, even bulk/direct SQL `INSERT` or `UPDATE` statements bypassing application procedures are intercepted before row storage.
- Verified in `DO` block: direct `INSERT` (`110.00 -> 104.50`) and direct `UPDATE` (`current_reading = 95.00` vs `previous_reading = 100.00`) were both aborted and `COUNT(*)` on `readings` remained `6`.

### (e) Overdue Bills View `v_overdue_bills` `[5 marks]`

```sql
CREATE OR REPLACE VIEW v_overdue_bills AS
SELECT
    c.full_name,
    b.due_on,
    (b.charge - b.amount_paid)::NUMERIC(10,2) AS outstanding_amount
FROM bills b
JOIN readings r  ON r.reading_id = b.reading_id
JOIN customers c ON c.customer_id = r.customer_id
WHERE b.due_on < CURRENT_DATE
  AND b.amount_paid < b.charge;
```

### (f) Partial Index `idx_bills_overdue_unpaid` `[5 marks]`

```sql
CREATE INDEX idx_bills_overdue_unpaid
ON bills (due_on)
WHERE amount_paid < charge;
```

**Justification:**
1. **High Selectivity Over Time:** In an operational utility billing system, the vast majority of historical bills (90%–99%+) are eventually settled (`amount_paid = charge`). Indexing `due_on` across *all* rows wastes B-tree pages and write I/O on closed historical bills that arrears queries never inspect.
2. **Exact Predicate Alignment:** The partial predicate `WHERE amount_paid < charge` indexes *only* open/unpaid bills, while the key `(due_on)` directly satisfies range predicates (`due_on < CURRENT_DATE`, aging buckets, and `ORDER BY due_on`) without an extra sort step.
3. **Reduced Maintenance Cost:** Once a bill is paid in full, it leaves the partial index, keeping index size proportional to active arrears rather than total company history.

**Actual PostgreSQL 18.6 `EXPLAIN` Plan (`enable_seqscan = off` on the 6-row seed table):**
```text

----------------------------------------------------

   Index Cond: (due_on < CURRENT_DATE)
(2 rows)
```

### (g) Scheduled Job `pr_refresh_receivables` `[6 marks]`

```sql
CREATE OR REPLACE PROCEDURE pr_refresh_receivables()
LANGUAGE plpgsql
AS $$
DECLARE
    v_total_due NUMERIC(12,2);
BEGIN
    SELECT COALESCE(SUM(charge - amount_paid), 0.00)::NUMERIC(12,2)
    INTO v_total_due
    FROM bills
    WHERE amount_paid < charge;

    INSERT INTO receivable_snapshot (snapshot_date, total_due)
    VALUES (CURRENT_DATE, v_total_due)
    ON CONFLICT (snapshot_date) DO UPDATE
        SET total_due = EXCLUDED.total_due;
END;
$$;
```

**Rerun & Same-Date Replacement Verification:**
1. **Run 1:** Inserts `(2026-11-24, 303.50)` (`32.50 + 55.00 + 116.00 + 100.00`).
2. **Run 2 (immediate rerun):** `ON CONFLICT (snapshot_date) DO UPDATE` keeps 1 row `(2026-11-24, 303.50)` — zero duplicate-key errors and no double counting.
3. **Run 3 (after recording a `K20.00` payment on Bill 5):** Replaces the same date's snapshot cleanly with `(2026-11-24, 283.50)`.

**Scheduler Registration (`00:30` Daily — `30 0 * * *`):**
- `solution.sql` includes the `pg_cron` registration (`cron.schedule('q07_daily_receivables_snapshot', '30 0 * * *', 'CALL q07_water_billing.pr_refresh_receivables();')`) guarded by an extension check.
- **Local Windows PostgreSQL 18.6 Note:** Because `pg_cron` and `pgAgent` are not installed on the local Windows PostgreSQL 18.6 instance, the script emits a clean `NOTICE` and exits with code `0`. On Windows deployments without `pg_cron`, the same procedure is triggered at `00:30` daily via Windows Task Scheduler (`psql -d ict371_final -c "CALL q07_water_billing.pr_refresh_receivables();"`) or `pgAgent`.
